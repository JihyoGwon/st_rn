# 코칭 시스템 아키텍처 비교 분석

## 방식 1: 채팅 내부 메타데이터 방식 (Embedded)

### 구조
```
채팅 파일: user/chats/{characterId}/chat.jsonl
├── 첫 줄: { 
│     chat_metadata: { 
│       coaching: { sessionId, goals, assessments, ... } 
│     },
│     user_name, character_name 
│   }
└── 메시지들: { name, mes, extra: { coaching: { ... } } }
```

### 특징
- 코칭 데이터가 채팅 파일에 직접 포함됨
- 채팅과 코칭이 강하게 결합됨 (1:1 또는 1:N 관계)
- 채팅 파일 하나에 모든 데이터가 포함됨

### 장점

#### 1. 구현 단순성
- **난이도**: ⭐⭐☆☆☆ (낮음)
- 별도 저장소 관리 불필요
- 기존 채팅 저장/로드 로직 재사용 가능
- 메타데이터만 추가하면 됨

#### 2. 데이터 일관성
- 채팅과 코칭 데이터가 항상 동기화됨
- 데이터 불일치 문제 없음
- 백업/복원이 단순함 (파일 하나만)

#### 3. 성능
- 채팅 로드 시 코칭 데이터도 함께 로드됨
- 별도 파일 I/O 불필요
- 네트워크 요청 횟수 감소

#### 4. 개발 속도
- 빠른 프로토타이핑 가능
- 기존 코드 수정 최소화
- 테스트가 단순함

### 단점

#### 1. 데이터 지속성 문제 ⚠️
- **채팅 삭제 시 코칭 데이터도 함께 삭제됨**
- 요구사항 2번과 충돌: "채팅 삭제해도 코칭 데이터는 남아있어야 함"
- 해결 방법: 채팅 삭제 시 코칭 데이터를 별도로 백업/마이그레이션 필요

#### 2. 확장성 제한
- 하나의 코칭 세션이 여러 채팅에 걸쳐 있을 때 관리 어려움
- 채팅 간 코칭 데이터 공유가 복잡함
- 코칭 세션 히스토리 추적이 어려움

#### 3. 데이터 크기
- 코칭 데이터가 많아지면 채팅 파일이 커짐
- 채팅 로드 시 불필요한 코칭 데이터도 함께 로드됨
- 메모리 사용량 증가

#### 4. 유연성 부족
- 코칭 세션을 독립적으로 관리하기 어려움
- 코칭 전용 기능 추가 시 제약이 많음
- 채팅과 코칭의 라이프사이클이 강하게 결합됨

### 구현 고려사항

#### 채팅 삭제 처리
```javascript
// 채팅 삭제 시 코칭 데이터 백업 필요
router.post('/delete', async (req, res) => {
  const chatData = getChatData(chatFilePath);
  const coachingData = chatData[0]?.chat_metadata?.coaching;
  
  if (coachingData) {
    // 코칭 데이터를 별도 저장소로 백업
    await backupCoachingData(coachingData);
  }
  
  // 채팅 파일 삭제
  fs.unlinkSync(chatFilePath);
});
```

#### 코칭 데이터 복원
- 채팅 삭제 후 복원 시 코칭 데이터도 함께 복원 필요
- 백업된 코칭 데이터를 새 채팅에 연결하는 로직 필요

## 방식 2: 별도 엔티티 관리 방식 (Separated)

### 구조
```
채팅 파일: user/chats/{characterId}/chat.jsonl
├── 첫 줄: { 
│     chat_metadata: { 
│       coaching_session_id: "session-123"  // 참조만
│     },
│     user_name, character_name 
│   }
└── 메시지들: { name, mes, extra: { coaching: { sessionId, ... } } }

별도 코칭 세션 파일: user/coaching/{sessionId}.json
└── {
      sessionId: "session-123",
      characterId: "character-abc",
      startTime: 1234567890,
      goals: { ... },
      assessments: { ... },
      actionPlans: { ... },
      relatedChats: ["chat-1", "chat-2"],  // 여러 채팅 참조 가능
      ...
    }
```

### 특징
- 코칭 데이터가 별도 파일/저장소에 저장됨
- 채팅과 코칭이 느슨하게 결합됨 (참조 관계)
- 코칭 세션이 독립적인 라이프사이클을 가짐

### 장점

#### 1. 데이터 지속성 ✅
- **채팅 삭제해도 코칭 데이터는 유지됨**
- 요구사항 2번을 자연스럽게 만족
- 코칭 세션을 독립적으로 관리 가능

#### 2. 확장성
- 하나의 코칭 세션이 여러 채팅에 걸쳐 있을 수 있음
- 채팅 간 코칭 데이터 공유가 쉬움
- 코칭 세션 히스토리 추적이 명확함

#### 3. 유연성
- 코칭 세션을 독립적으로 시작/종료/일시정지 가능
- 코칭 전용 기능 추가가 자유로움
- 채팅과 코칭의 라이프사이클이 분리됨

#### 4. 데이터 관리
- 코칭 데이터만 따로 백업/복원 가능
- 코칭 데이터 검색/필터링이 쉬움
- 코칭 전용 분석 기능 구현이 용이함

#### 5. 사용성
- 코칭 세션 목록을 독립적으로 표시 가능
- 진행 중인 코칭 세션을 쉽게 찾을 수 있음
- 코칭 대시보드 구현이 자연스러움

### 단점

#### 1. 구현 복잡도
- **난이도**: ⭐⭐⭐⭐☆ (중상)
- 별도 저장소 관리 필요
- 채팅-코칭 간 동기화 로직 필요
- 데이터 불일치 가능성

#### 2. 성능 오버헤드
- 채팅 로드 시 코칭 데이터를 별도로 로드해야 함
- 추가 파일 I/O 발생
- 네트워크 요청 횟수 증가

#### 3. 동기화 복잡도
- 채팅과 코칭 데이터 간 일관성 유지 필요
- 참조 무결성 관리 필요
- 오래된 참조(orphaned references) 처리 필요

#### 4. 개발 시간
- 초기 구현 시간이 더 걸림
- 테스트 시나리오가 복잡해짐
- 디버깅이 어려울 수 있음

### 구현 고려사항

#### 코칭 세션 저장소 구조
```
user/coaching/
├── sessions/
│   ├── {sessionId}.json          # 코칭 세션 메타데이터
│   └── {sessionId}-history.json  # 세션 히스토리 (선택적)
└── index.json                    # 세션 인덱스 (빠른 검색용)
```

#### 채팅-코칭 연결 관리
```javascript
// 채팅 저장 시 코칭 세션 연결
router.post('/save', async (req, res) => {
  const chatData = req.body.chat;
  const sessionId = chatData[0]?.chat_metadata?.coaching_session_id;
  
  if (sessionId) {
    // 코칭 세션에 채팅 ID 추가
    await addChatToSession(sessionId, chatId);
  }
  
  // 채팅 저장
  await saveChat(chatData);
});

// 코칭 세션 조회 시 관련 채팅들도 함께 로드
async function getCoachingSession(sessionId) {
  const session = await loadCoachingSession(sessionId);
  const relatedChats = await loadRelatedChats(session.relatedChats);
  return { ...session, chats: relatedChats };
}
```

#### 데이터 정합성 유지
- 채팅 삭제 시 코칭 세션의 `relatedChats`에서 제거
- 코칭 세션 삭제 시 채팅의 `coaching_session_id` 제거
- 정기적인 데이터 정합성 검사 필요

## 하이브리드 방식 (Hybrid)

### 개념
- 기본적으로는 별도 엔티티 방식 사용
- 하지만 채팅 메타데이터에도 최소한의 코칭 정보 포함 (캐싱 목적)
- 코칭 세션이 활성화된 채팅에만 메타데이터 포함

### 구조
```
채팅 파일: user/chats/{characterId}/chat.jsonl
├── 첫 줄: { 
│     chat_metadata: { 
│       coaching_session_id: "session-123",
│       coaching_summary: { ... }  // 캐싱용 최소 정보
│     }
│   }

별도 코칭 세션: user/coaching/{sessionId}.json
└── { 전체 코칭 데이터 }
```

### 장점
- 별도 엔티티의 장점 + 채팅 로드 시 빠른 접근
- 데이터 지속성 보장
- 성능 최적화 가능

### 단점
- 두 저장소 간 동기화 필요
- 구현 복잡도가 가장 높음

## 사용 시나리오별 비교

### 시나리오 1: 자연스러운 코칭 (현재 우선순위)

#### 방식 1 (Embedded)
- ✅ 채팅 시작 시 자동으로 코칭 세션 시작
- ✅ 메시지마다 코칭 데이터 업데이트
- ❌ 채팅 삭제 시 코칭 데이터 손실 (문제)

#### 방식 2 (Separated)
- ✅ 채팅 시작 시 코칭 세션 자동 생성
- ✅ 메시지마다 코칭 세션 업데이트
- ✅ 채팅 삭제해도 코칭 데이터 유지
- ⚠️ 코칭 세션 조회 시 추가 로드 필요

### 시나리오 2: 명시적 코칭 세션 관리 (향후 확장)

#### 방식 1 (Embedded)
- ❌ 여러 채팅에 걸친 코칭 세션 관리 어려움
- ❌ 코칭 세션 목록 표시가 복잡함
- ❌ 세션 시작/종료가 채팅에 종속됨

#### 방식 2 (Separated)
- ✅ 여러 채팅에 걸친 코칭 세션 자연스럽게 지원
- ✅ 코칭 세션 목록 표시가 쉬움
- ✅ 세션 시작/종료가 독립적

## 앱 컨셉 및 사용성 고려

### 현재 컨셉: "자연스러운 코칭"
- 사용자가 명시적으로 코칭 세션을 시작하지 않음
- 일반 채팅 중 자연스럽게 코칭이 이뤄짐
- 하지만 코칭 데이터는 유지되어야 함

### 방식 1의 문제점
- 채팅 삭제 시 코칭 데이터 손실
- 사용자가 "이 채팅은 삭제하고 싶지만 목표는 남기고 싶어" 할 때 불가능

### 방식 2의 장점
- 사용자가 채팅을 삭제해도 목표/진행 상황은 유지
- 나중에 "내 목표는 뭐였지?" 확인 가능
- 코칭 대시보드 구현이 자연스러움

### 향후 확장성
- 코칭 세션 목록 화면 추가 시: 방식 2가 훨씬 자연스러움
- 여러 채팅에 걸친 장기 코칭: 방식 2만 가능
- 코칭 리포트 생성: 방식 2가 적합

## 권장사항

### 단기 (MVP)
**방식 2 (Separated)를 권장하지만, 단순화된 버전으로 시작**

이유:
1. 요구사항 2번 (채팅 삭제해도 코칭 데이터 유지)을 만족해야 함
2. 향후 확장성을 고려하면 방식 2가 유리함
3. 초기에는 최소 기능만 구현하여 복잡도 관리

### 구현 전략
1. **Phase 1**: 기본 코칭 세션 저장소만 구현
2. **Phase 2**: 채팅-코칭 연결 로직 추가
3. **Phase 3**: 고급 기능 (여러 채팅 연결 등) 추가

### 단순화 방안
- 초기에는 1:1 관계만 지원 (하나의 코칭 세션 = 하나의 채팅)
- 나중에 N:1 관계 추가 (여러 채팅 = 하나의 코칭 세션)
- 코칭 세션 인덱스는 나중에 추가

## 결론

### 방식 1 (Embedded)
- ✅ 빠른 구현
- ✅ 단순한 구조
- ❌ 요구사항 2번 미충족
- ❌ 확장성 제한

### 방식 2 (Separated)
- ✅ 요구사항 2번 충족
- ✅ 확장성 우수
- ✅ 향후 기능 추가 용이
- ⚠️ 구현 복잡도 높음
- ⚠️ 초기 개발 시간 더 필요

### 최종 권장: **방식 2 (Separated) - 단순화된 버전**

요구사항 2번을 만족하고 향후 확장성을 고려하면 방식 2가 적합함.
초기에는 최소 기능만 구현하여 복잡도를 관리하고, 점진적으로 기능을 확장하는 전략을 권장함.
