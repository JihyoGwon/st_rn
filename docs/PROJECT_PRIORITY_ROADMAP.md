# 프로젝트 우선순위 로드맵

## 📋 개요

4가지 주요 작업의 우선순위와 실행 순서를 결정하는 전략 문서입니다.

## 🎯 작업 목록

1. **실리태번 기능 완성** - 아직 앱에 못 붙인 기능들 구현
2. **필수 기능 구현** - 앱에 필수인 새로운 기능/시스템 구현
3. **데이터베이스 전환** - 파일시스템 → 데이터베이스 마이그레이션
4. **불필요한 기능 제거** - 점진적 기능 제거로 복잡도 감소

## 📊 각 작업 분석

### 1. 실리태번 기능 완성

**특징**:
- 비즈니스 가치: ⭐⭐⭐⭐ (높음)
- 기술 부채: ⭐⭐⭐⭐⭐ (기술 부채 유지)
- 작업량: 중간 (2-4주)
- 리스크: 낮음 (기존 기능 활용)

**의존성**:
- 다른 작업과 독립적
- DB 전환 전/후 모두 가능

**장점**:
- 빠른 사용자 가치 제공
- 기능 완성도 향상

**단점**:
- 기술 부채 누적
- 나중에 DB 전환 시 추가 작업 필요

---

### 2. 필수 기능 구현

**특징**:
- 비즈니스 가치: ⭐⭐⭐⭐⭐ (매우 높음)
- 기술 부채: ⭐⭐⭐⭐⭐ (기술 부채 유지)
- 작업량: 중간-높음 (3-6주)
- 리스크: 중간 (새로운 기능)

**의존성**:
- DB 전환 전에 하면: 파일 시스템 기반으로 구현 → 나중에 DB로 마이그레이션 필요
- DB 전환 후에 하면: DB 기반으로 처음부터 구현 → 더 깔끔함

**장점**:
- 핵심 비즈니스 가치
- 출시에 필수

**단점**:
- DB 전환 전에 하면 이중 작업 (파일 → DB)
- 기술 부채 누적

---

### 3. 데이터베이스 전환

**특징**:
- 비즈니스 가치: ⭐⭐⭐ (중간, 장기적 가치)
- 기술 부채: ⭐ (기술 부채 해결)
- 작업량: 높음 (5-8주)
- 리스크: 높음 (큰 변경)

**의존성**:
- 다른 작업의 기반이 됨
- 이후 작업들이 DB 기반으로 구현 가능

**장점**:
- 기술 부채 해결
- 확장성 확보
- 이후 작업의 기반

**단점**:
- 시간이 오래 걸림
- 높은 리스크
- 즉시 사용자 가치 없음

---

### 4. 불필요한 기능 제거

**특징**:
- 비즈니스 가치: ⭐⭐ (낮음, 유지보수성 향상)
- 기술 부채: ⭐⭐ (일부 해결)
- 작업량: 낮음 (1-2주)
- 리스크: 낮음 (점진적 제거)

**의존성**:
- DB 전환 전에 하면: 제거할 기능을 DB로 마이그레이션할 필요 없음
- DB 전환 후에 하면: 이미 DB로 마이그레이션한 기능을 제거 (낭비)

**장점**:
- 빠른 복잡도 감소
- 유지보수성 향상
- 낮은 리스크

**단점**:
- 즉시 사용자 가치 없음
- 작은 영향

---

## 🎯 추천 우선순위

### 옵션 A: 빠른 출시 우선 (추천)

```
순서: 4 → 2 → 1 → 3
```

**이유**:
1. **4번 (기능 제거)** - 빠르게 복잡도 감소 (1-2주)
2. **2번 (필수 기능)** - 출시에 필수, 빠른 가치 제공 (3-6주)
3. **1번 (기능 완성)** - 사용자 경험 개선 (2-4주)
4. **3번 (DB 전환)** - 장기적 기반 마련 (5-8주)

**장점**:
- 빠른 출시 가능
- 사용자 가치 빠르게 제공
- 기술 부채는 있지만 작동하는 제품

**단점**:
- 기술 부채 누적
- 나중에 DB 전환 시 추가 작업

**총 기간**: 11-20주 (약 3-5개월)

---

### 옵션 B: 기술 부채 해결 우선

```
순서: 4 → 3 → 2 → 1
```

**이유**:
1. **4번 (기능 제거)** - 빠르게 복잡도 감소 (1-2주)
2. **3번 (DB 전환)** - 기술 부채 해결, 이후 작업의 기반 (5-8주)
3. **2번 (필수 기능)** - DB 기반으로 깔끔하게 구현 (3-6주)
4. **1번 (기능 완성)** - DB 기반으로 구현 (2-4주)

**장점**:
- 기술 부채 해결
- 이후 작업들이 깔끔함
- 장기적 유지보수성 향상

**단점**:
- 출시가 늦어짐
- 즉시 사용자 가치 없음

**총 기간**: 11-20주 (약 3-5개월)

---

### 옵션 C: 하이브리드 (균형)

```
순서: 4 → 2 (핵심만) → 3 → 2 (나머지) → 1
```

**이유**:
1. **4번 (기능 제거)** - 빠르게 복잡도 감소 (1-2주)
2. **2번 (필수 기능 - 핵심만)** - 출시에 꼭 필요한 것만 (1-2주)
3. **3번 (DB 전환)** - 기술 부채 해결 (5-8주)
4. **2번 (필수 기능 - 나머지)** - DB 기반으로 나머지 구현 (2-4주)
5. **1번 (기능 완성)** - DB 기반으로 구현 (2-4주)

**장점**:
- 빠른 출시 (핵심 기능만)
- 기술 부채 해결
- 균형잡힌 접근

**단점**:
- 일부 기능은 이중 작업 (파일 → DB)

**총 기간**: 11-20주 (약 3-5개월)

## 🎯 최종 추천: 옵션 A (빠른 출시 우선)

### 실행 계획

#### Phase 1: 복잡도 감소 (1-2주)
```
✅ 불필요한 기능 제거
- 웹 전용 기능 제거 (stats, themes, moving-ui 등)
- 외부 서비스 직접 통합 제거 (OpenRouter로 통합)
- 예상 효과: 엔드포인트 251개 → 150개
```

#### Phase 2: 필수 기능 구현 (3-6주)
```
✅ 앱에 필수인 새로운 기능 구현
- 예: 로그인 시스템, 사용자 관리 등
- 파일 시스템 기반으로 구현 (빠른 출시)
- 나중에 DB 전환 시 마이그레이션
```

#### Phase 3: 기능 완성 (2-4주)
```
✅ 실리태번 기능 중 앱에 못 붙인 것들 구현
- 예: World Info, 벡터 검색 등 (필요한 것만)
- 파일 시스템 기반으로 구현
```

#### Phase 4: 데이터베이스 전환 (5-8주)
```
✅ 파일 시스템 → 데이터베이스 마이그레이션
- 하이브리드 모드로 안전하게 전환
- 점진적 마이그레이션
- 기술 부채 해결
```

### 타임라인

```
Week 1-2:   기능 제거 (복잡도 감소)
Week 3-8:   필수 기능 구현 (출시 준비)
Week 9-12:  기능 완성 (사용자 경험 개선)
Week 13-20: DB 전환 (기술 부채 해결)
```

**총 기간**: 약 5개월

---

## ⚠️ 주의사항

### 옵션 A 선택 시

1. **기술 부채 관리**
   - DB 전환 전까지 기술 부채 누적
   - 하지만 작동하는 제품이 우선

2. **마이그레이션 계획**
   - 필수 기능을 파일 시스템으로 구현하더라도
   - DB 전환 시 마이그레이션 계획 수립

3. **점진적 접근**
   - 한 번에 모든 것을 하지 않기
   - 단계별로 검증하며 진행
